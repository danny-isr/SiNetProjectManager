# אפיון תהליך עבודה למיילים וקבצים ב-ACC

## 1. תרשים זרימה כללי

```text
מייל מתקבל
↓
זיהוי קבצים מצורפים וקישורים חיצוניים
↓
העלאת כל החומר ל-ACC Inbox
↓
שיוך המייל לפרויקט
↓
טעינת יעדי תיוג מתוך ProjectFile
↓
בחירת יעד לכל קובץ / תיקייה
↓
בניית נתיב יעד מתוך עץ התיקיות
↓
העתקת החומר לתיקיית הפרויקט ב-ACC
↓
השארת העותק ב-Inbox כמקור אמת
```

## 2. תרשימי ארכיטקטורה

### 2.1 מבנה הפרויקט ב‑ACC

```text
ACC Project: SI-<Place>
│
├── (Parent Project ProjectFolder)  ← אם קיים פרויקט אב
│     └── (Project ProjectFolder)
│           └── עץ התיקיות הרגיל מהדאטהבייס
│                 ├── ProjectFolder
│                 │    └── Subfolder
│                 └── ProjectFile targets לפי המבנה הקיים
```

הערה חשובה:

* אחרי תיקיית הפרויקט אין שכבת ביניים כללית כמו `Discipline / File Structure`.
* בתוך תיקיית הפרויקט נבנה **ישר** עץ התיקיות הרגיל כפי שהוא מוגדר כיום בדאטהבייס ובמערכת הקיימת.
* כלומר, מבנה ה-ACC צריך לשקף את עץ התיקיות הקיים, בלי להוסיף שכבות מלאכותיות חדשות.

### 2.2 זרימת מידע מהמערכת ל‑ACC

```text
Email arrives
      ↓
Attachments detected
      ↓
Upload to ACC Inbox
      ↓
User assigns Email to Project
      ↓
Load tag targets (ProjectFile filtered by ProjectType + OutSideData)
      ↓
User selects destination
      ↓
System builds folder path from ProjectFolder tree (Parent → Child)
      ↓
Copy file to ACC Project folder
      ↓
File remains in Inbox as source of truth
```

## 2. מטרה

להגדיר תהליך עבודה מלא לטיפול במיילים נכנסים, בקבצים המצורפים אליהם, ובהעלאתם ל-ACC, כך שכל חומר שמתקבל יישמר תחילה באזור Inbox ייעודי, יוצג בצורה אחידה למשתמש, ובהמשך יוכל להיות משויך לפרויקט, מתויג לפי סוג קובץ/נושא, ומועתק למיקום המתאים במבנה הפרויקט ב-ACC.

## 3. עקרונות יסוד

1. קליטת קבצים והשיוך לפרויקט הם שני שלבים נפרדים.
2. כל החומר שמגיע ממייל נשמר קודם כל ב-Inbox של המיילים ב-ACC.
3. רשימת יעדי התיוג אינה חופשית ואינה קשיחה בקוד.
4. מבנה היעדים ב-ACC צריך לשקף את מבנה סוגי הקבצים שכבר מוגדר אצלכם.
5. ה-Inbox נשאר מקור האמת גם לאחר העתקה לפרויקט.

## 4. ישויות ומקורות נתונים

### 4.1 פרויקט

* השדה הקובע את ה-Place (עיר/מקום כפי שמוגדר בשדה Place בפרויקט) הוא `Place`.
* לכל פרויקט יש מספר פרויקט, שם פרויקט, וייתכן גם פרויקט אב.

### 4.2 סוגי קבצים ויעדי תיוג

המקור הוא הטבלה:

* `SiData.dbo.ProjectFile`

רק רשומות שמסומנות כ-`OutSidData` הן יעדי תיוג אפשריים.

### 4.3 משתמשים והרשאות ACC

המקור הוא הטבלה:

* `SiData.dbo.SIUser`

מיפוי `AccUserType`:

* `NoAccUser = 0` – אין למשתמש גישת ACC
* `Engineer = 1` – יש להוסיף את המשתמש ל-ACC בתפקיד `Member`
* `Admin = 2` – יש להוסיף את המשתמש ל-ACC בתפקיד `Project Admin`

כלל הצירוף לפרויקט חדש:

* יש לצרף רק משתמשים שבהם `IsActive = true`
* ורק משתמשים שבהם `AccUserType != NoAccUser`

### 4.4 עץ תיקיות

מבנה התיקיות נבנה מתוך עץ תיקיות היררכי:

* לכל ProjectFolder יש תיקיית אב
* התיקייה שבה `INFOLDERID = NULL` היא תיקיית השורש
* משם בונים את כל ההיררכיה כלפי מטה, מאב לבן

## 5. שלב 1 – קליטת מיילים

המערכת מקבלת מיילים ומציגה אותם למשתמש.

במערכת הקיימת כבר יש:

* טעינת מיילים מ-Gmail API
* Pagination
* קיבוץ ומיון
* תצוגת גוף מייל
* תצוגת קבצים מצורפים

## 6. שלב 2 – זיהוי החומר שהגיע עם המייל

### 6.1 קבצים מצורפים רגילים

* המערכת מזהה אותם אוטומטית מתוך המייל
* מציגה אותם ברשימת הקבצים של המייל
* מסמנת אותם כקובץ מצורף רגיל

### 6.2 קבצים שהגיעו דרך קישור

כאשר במייל יש קישור להורדת חומר:

1. המשתמש פותח את הקישור
2. נפתח חלון חיצוני / פופ-אפ לדף ההורדה
3. המשתמש לוחץ Download
4. המערכת מזהה שהתחילה/הסתיימה הורדה
5. המערכת שואלת האם להעלות את הקובץ ל-ACC Inbox
6. אם המשתמש מאשר – המערכת מעלה את הקובץ ל-ACC Inbox
7. לאחר מכן הקובץ מתווסף גם לרשימת הקבצים של אותו מייל כ-Attachment נוסף

### 6.3 ZIP ותיקייה שחולצה

אם אחד הקבצים הוא ZIP:

1. המערכת מעלה את קובץ ה-ZIP עצמו ל-ACC Inbox
2. המערכת מחלצת את תוכן ה-ZIP
3. המערכת מעלה גם את התוכן שחולץ
4. תיוג של תיקייה כרגע קובע רק לאיזה מקום התיקייה תועתק

### 6.4 תצוגה מאוחדת

ברמת המייל, כל החומר צריך להופיע תחת רשימת Attachments אחת, עם הבחנה ברורה בין:

* קובץ מצורף רגיל
* קובץ שהגיע מקישור
* קובץ ZIP
* תיקייה שחולצה מ-ZIP

## 7. שלב 3 – חיווי חזותי בממשק

לכל פריט ברשימת הקבצים צריך להיות סימון ברור:

* קובץ רגיל – אייקון של Attachment רגיל
* קובץ שהגיע מלינק – אייקון ייעודי נפרד
* בתהליך העלאה – אייקון של Uploading
* הועלה ל-ACC – אייקון/Badge שמראה שניתן לצפות בקובץ ב-ACC
* נכשל – חיווי שגיאה ברור

צפייה דרך ACC אפשרית רק לאחר שהקובץ עלה בפועל ל-ACC.

## 8. שלב 4 – העלאה ל-ACC Inbox

כל הקבצים שמגיעים מהמיילים נשמרים תחילה ב-ACC Inbox ייעודי.

מטרת התיקייה הזו:

* לשמש אזור קליטה ראשוני לכל חומר שמגיע במייל
* להפריד בין שלב הקליטה לבין שלב התיוק לפרויקט
* לאפשר בקרה ותצוגה לפני העתקה ליעד הסופי

אם העלאה ל-ACC נכשלת:

* יש לנסות שוב אוטומטית
* עד שלוש פעמים
* אם לאחר שלושה ניסיונות העלאה עדיין נכשלה, יש להודיע למשתמש שההעלאה נכשלה

## 9. שלב 5 – קביעת מבנה הפרויקט ב-ACC

### 9.1 כלל כללי

* במערכת המקומית התיקייה הראשית היא לפי השדה `Place` של הפרויקט
* ב-ACC כל ערך של `Place` ממופה לפרויקט ACC נפרד
* שם הפרויקט ב-ACC נבנה תמיד לפי הפורמט: `SI-` + `Place`

לדוגמה:

* `SI-<Place>`
* לדוגמה: `SI-אשקלון` כאשר `Place = אשקלון`

### 9.2 יצירת פרויקט ACC אם אינו קיים

1. קוראים את `Place` של הפרויקט
2. מחפשים פרויקט ACC בשם `SI-` + `Place`
3. אם הפרויקט לא קיים – יוצרים אותו אוטומטית
4. בזמן יצירת פרויקט ACC חדש, המערכת מוסיפה אליו משתמשים לפי טבלת `SIUser`

### 9.3 מבנה תיקיות הפרויקט

שם תיקיית הפרויקט הוא בפורמט:

* `(` + מספר פרויקט + `)` + שם פרויקט מנורמל

נרמול שם הפרויקט יתבצע באמצעות אותה פונקציה קיימת שכבר משמשת כיום ליצירת שמות תיקיות במערכת הכללית.

כאשר יש פרויקט אב:

* קודם תיווצר תיקייה של פרויקט האב
* מתחתיה תיווצר תיקייה של הפרויקט הספציפי
* בתוך תיקיית הפרויקט הספציפי ייבנה מבנה הקבצים המלא

דוגמה למבנה מקומי:

* `U:\אשקלון\(2621)שביל_אופניים_ברחוב_בר_לב`

התרגום ל-ACC:

* Project ב-ACC: `SI-אשקלון`
* בתוך הפרויקט: תיקיית הפרויקט `(2621)שביל_אופניים_ברחוב_בר_לב`
* ואם יש פרויקט אב: תיקיית אב → תיקיית הפרויקט → מבנה הקבצים המלא

## 10. שלב 6 – שיוך מייל לפרויקט

שיוך מייל לפרויקט הוא שלב נפרד משלב קליטת הקבצים.

כלומר:

* לא חייבים לשייך לפרויקט בזמן הורדת קובץ מקישור
* קודם כל מעלים ל-ACC Inbox
* רק לאחר מכן המשתמש מבצע File Email / שיוך לפרויקט

## 11. שלב 7 – טעינת יעדי התיוג

כאשר המייל כבר משויך לפרויקט:

1. המערכת טוענת את רשימת הרשומות מ-`ProjectFile`
2. היא מסננת אותן לפי סוגי הפרויקט של הפרויקט הנוכחי
3. עבור כל `ProjectType` של הפרויקט מאתרים את רשומות `ProjectFile` ששייכות לאותו `ProjectType`
4. מתוך הרשומות האלו מוצגים רק פריטים שמסומנים כ-`OutSidData`
5. מבנה התיקיות והיעדים נגזר מאותו עץ תיקיות שכבר נבנה כיום מהדאטהבייס במערכת המקומית
6. אין להמציא מבנה חדש ל-ACC, אלא להשתמש באותו מנגנון קיים שכבר בונה את עץ התיקיות המקומי
7. הרשימה שמוצגת למשתמש ממוינת לפי:

   * קודם תיקייה
   * אחר כך `Title`

## 12. שלב 8 – תיוג קבצים

1. המשתמש בוחר עבור כל קובץ או תיקייה את היעד המתאים
2. הבחירה נשמרת על גבי אותו Attachment / ProjectFolder Unit
3. היעד שנבחר קובע לאן הקובץ יועתק בפרויקט

הצגה מומלצת ברשימה:

* שם תיקייה
* אחריו שם הקובץ / `Title`

## 13. שלב 9 – בניית נתיב היעד

הנתיב אינו נלקח משדה טקסט אחד, אלא נבנה דינמית מתוך עץ התיקיות:

* מתחילים בתיקיית השורש שבה `INFOLDERID = NULL`
* בונים את ההיררכיה מאב לבן
* ממקמים את `ProjectFile` הנבחר בתוך עץ התיקיות הזה
* כך מתקבל היעד הסופי בתוך הפרויקט ב-ACC

## 14. שלב 10 – העתקה לפרויקט ב-ACC

לאחר שמייל משויך לפרויקט ולאחר שכל Attachment קיבל יעד/תיוג:

1. המערכת מאתרת את מיקום היעד המתאים בפרויקט
2. אם צריך – יוצרת את תיקיית היעד ב-ACC
3. מעתיקה את הקובץ/התיקייה מה-Inbox אל תיקיית הפרויקט
4. אם פעולת ההעתקה לא החזירה שגיאה, מבחינת המערכת הפעולה נחשבת כמוצלחת
5. העותק ב-Inbox נשאר ואינו נמחק

### 14.1 קובץ זהה

אם בפרויקט כבר קיים קובץ עם:

* אותו שם
* אותו גודל
* ואותו תאריך עדכון

זה נחשב קובץ זהה.

במקרה כזה יוצג למשתמש:

`A file with the same name, size and modification date already exists.`

`What would you like to do?`

אפשרויות:

* **Skip**
* **Upload as new version**
* **Rename**

### 14.2 גרסאות

אם אחד מהפרמטרים שונה, ובפרט אם הקובץ החדש מעודכן יותר:

* יש להעלות אותו באותו שם
* ולהשתמש במנגנון הגרסאות של ACC

## 15. שלב 11 – חוקים משלימים

1. Inbox הוא מקור האמת של עולם המיילים
2. פרויקט ACC חדש נוצר לפי `SI-` + `Place`
3. פרויקט ACC חדש מקבל רק משתמשים פעילים עם גישת ACC
4. תיוג תיקייה כרגע קובע יעד מיקום בלבד
5. זיהוי אוטומטי של קישורים חיצוניים הוא פיצ'ר עתידי
6. מנוע AI מקומי הוא פיצ'ר עתידי

## 16. מודל הרשאות ACC (Roles ו‑Access Levels)

כדי שהמערכת תעבוד בצורה יציבה עם ACC API יש להגדיר הרשאות לפי שלוש שכבות שונות במערכת ACC.

### 16.1 Project Role

זהו התפקיד של המשתמש בתוך הפרויקט.

התפקיד משמש בעיקר להגדרה ארגונית ואינו שולט ישירות בהרשאות הקבצים.

התפקידים שבהם המערכת משתמשת:

| AccUserType | Role ב‑ACC    |
| ----------- | ------------- |
| Engineer    | Member        |
| Admin       | Project Admin |

### 16.2 Product Access

משתמש חייב לקבל גישה למוצר **Docs** כדי שיוכל לעבוד עם הקבצים בפרויקט.

לכן בעת יצירת פרויקט או הוספת משתמש:

* יש לוודא ש‑Docs access מופעל

### 16.3 ProjectFolder Permissions (Access Level)

זוהי רמת הגישה האמיתית לקבצים והתיקיות.

הרשאות אפשריות במערכת ACC כוללות:

* View
* Download
* Upload
* Edit
* ProjectFolder Control (שליטה מלאה)

### 16.4 מודל הרשאות מומלץ למערכת

כדי למנוע בעיות בהרשאות וב‑API יש להשתמש במודל פשוט ואחיד:

| סוג משתמש | Project Role  | ProjectFolder Permission        |
| --------- | ------------- | ------------------------------- |
| Engineer  | Member        | View + Download + Upload + Edit |
| Admin     | Project Admin | ProjectFolder Control           |

### 16.5 הגדרת הרשאות בפועל

בעת יצירת פרויקט חדש:

1. המערכת יוצרת את פרויקט ACC.
2. מוסיפה משתמשים לפי טבלת `SIUser`.
3. מגדירה Product Access למוצר **Docs**.
4. מגדירה הרשאות **רק על תיקיית השורש** של מבנה הקבצים.

### 16.6 ירושת הרשאות

הרשאות בתיקיות ACC עובדות בירושה.

לכן:

* הרשאות מוגדרות רק על תיקיית השורש.
* כל תתי‑התיקיות יורשות את ההרשאות אוטומטית.

### 16.7 כלל חשוב למימוש

אין להגדיר הרשאות לכל תיקייה בנפרד.

ניהול הרשאות ברמת כל תיקייה עלול לגרום:

* לחוסר עקביות בהרשאות
* לכשלי API
* למשתמשים שלא מצליחים להגיע לקבצים

לכן כל מבנה הפרויקט מסתמך על הרשאות שמוגדרות **רק בשורש העץ**.

## 16. פערים מרכזיים למימוש

1. מנגנון מלא של העתקה מה-Inbox אל מבנה הפרויקט לפי היעד שנבחר
2. מנגנון Retry מלא ברמת Attachment בממשק
3. תמיכה מלאה בתיקייה כיחידה אחת בכל הזרימה
4. מימוש/חיבור מלא של יצירת פרויקט ACC חדש עם הרשאות משתמשים
5. מימוש ממשק משתמש מלא להודעות והתראות במקרי קובץ זהה וכשלי העלאה

## 17. מודל נתונים מרכזי (Data Model)

המערכת נשענת על מספר טבלאות מרכזיות במסד הנתונים. מטרת סעיף זה היא להציג את הקשרים בין הישויות העיקריות שמשתתפות בתהליך.

### 17.1 Project

מייצג פרויקט במערכת.

שדות חשובים:

* ProjectID
* Number
* Name
* Place
* ParentProjectID
* ProjectType

שימושים עיקריים:

* קביעת הפרויקט שאליו משויך המייל
* קביעת פרויקט ה‑ACC לפי הכלל `SI-` + `Place`
* קביעת מבנה תיקיות הפרויקט

### 17.2 ProjectFile

הטבלה שמגדירה את סוגי הקבצים והיעדים האפשריים.

שדות מרכזיים:

* ID
* Title
* Number
* des
* FOLDERID
* TypeProjID
* OutSidData

תפקידים:

* קביעת יעד התיוג
* קביעת מבנה תיקיות הקבצים
* סינון לפי סוג פרויקט

רק רשומות שבהן `OutSidData = true` מופיעות ברשימת היעדים למשתמש.

### 17.3 ProjectFolder

טבלה שמגדירה את עץ התיקיות.

מבנה היררכי:

* ProjectFolderID
* ProjectFolderName
* INFOLDERID

כללים:

* `INFOLDERID = NULL` מציין תיקיית שורש
* כל תיקייה אחרת מצביעה על תיקיית האב שלה

כך נבנה עץ התיקיות:

* Root

  * Discipline

    * Drawings
    * Models
  * Documents

### 17.4 SIUser

טבלת המשתמשים במערכת.

שדות מרכזיים:

* ID
* Name
* Email
* IsActive
* AccUserType

מיפוי ל‑ACC:

* Engineer → Member
* Admin → Project Admin

רק משתמשים שבהם:

* `IsActive = true`
* `AccUserType != NoAccUser`

נוספים לפרויקט ACC חדש.

### 17.5 EmailInboxAttachment

מייצג קובץ שהגיע ממייל.

שדות עיקריים:

* Id
* MessageId
* FileName
* FileSize
* AccItemId
* ProjectFileId
* IsExternalDownload

משמש עבור:

* שמירת הקובץ ב‑ACC Inbox
* שמירת תיוג הקובץ
* מעקב אחרי מצב ההעלאה

### 17.6 קשרים בין הטבלאות

Project

* קשור ל‑ProjectType
* ProjectType קובע אילו ProjectFile רלוונטיים

ProjectFile

* קשור ל‑ProjectFolder
* קובע את יעד התיוג במבנה התיקיות

EmailInboxAttachment

* יכול להיות מתויג ל‑ProjectFile
* קובע לאן הקובץ יועתק בתוך הפרויקט

SIUser

* מצורף לפרויקטי ACC בעת יצירת הפרויקט

### ZIP Extraction (Recursive)

חילוץ קבצי ZIP במערכת מתבצע בצורה **רקורסיבית**.

כללים:

* כאשר מתקבל קובץ ZIP הוא מחולץ לתיקייה.
* אם בתוך הקובץ קיימים קבצי ZIP נוספים — המערכת מחלצת גם אותם.
* התהליך ממשיך בצורה רקורסיבית עד שלא נשארים קבצי ZIP.

לאחר החילוץ:

* קבצי ZIP פנימיים **אינם נשמרים**.
* נשמרים רק הקבצים הסופיים והתיקיות שנוצרו.

דוגמה:

ZIP ├── plans.zip │     ├── drawing1.dwg │     └── drawing2.dwg └── documents └── report.pdf

התוצאה לאחר חילוץ:

folder ├── drawing1.dwg ├── drawing2.dwg └── documents └── report.pdf

כלומר קבצי ZIP ביניים אינם נשמרים במערכת או ב‑ACC.
