# 📘 מדריך בניית תבנית ביקורת — Google Sheets

> **גרסה:** 1.0 | **תאריך:** מרץ 2026  
> מדריך זה מיועד למנהלי מערכת ולבודקים המכינים תבניות ביקורת ב-Google Sheets.

---

## 1. מבוא

מערכת הביקורת מבוססת על **תגיות** (`<<...>>`) שמוטמעות בתוך תבנית Google Sheets.  
בעת יצירת דוח חדש, המערכת:

1. **סורקת** את כל התאים בגיליון ומזהה תגיות.
2. **מאמתת** את תקינות המבנה (צמדים, ייחודיות, עקביות).
3. **מסנכרנת** את מבנה הפרקים והסעיפים למסד הנתונים.
4. בעת **ייצוא** — מעתיקה את התבנית, מחליפה תגיות בנתונים אמיתיים.

### סוגי תגיות

| סוג | תבנית | דוגמה | תפקיד |
|-----|--------|--------|--------|
| **הגדרה (סטטוס)** | `<<X.Y כותרת [תוכן]>>` | `<<1.1 כללי [תרשים סביבה]>>` | מגדיר סעיף + מוחלף בסטטוס |
| **קלט הערות** | `<<X.Y $>>` | `<<1.1 $>>` | תא שבו יוזרקו הערות הבודק |
| **שדה כללי** | `<<שם>>` | `<<שם פרויקט>>` | שדה מטא-דאטה — מוחלף בערך מה-DB |

> **תגית חובה נוספת:** `<<תגובת המתכנן>>` — חייבת להופיע בתבנית **בדיוק פעם אחת**.
> התא שבו היא יושבת קובע את עמודת תגובות המתכנן בדוח ובייצוא. ראה [כלל 7](#כלל-7-עמודת-תגובת-המתכנן--חובה-missing_planner_response_tag--duplicate_planner_response_tag).

## 2. תגיות שדות כלליים (General Tags)

שדות כלליים הם תגיות **ללא מספר סעיף** — הם מוחלפים בנתוני פרויקט, דוח או משתמש.

### טבלת מיפוי מלאה

| תגית בתבנית | מקור נתונים | אוטומטי? | הערות |
|-------------|-------------|----------|-------|
| `<<שם פרויקט>>` | `Project.Title` | ✅ כן | שם הפרויקט מה-DB |
| `<<מספר פרויקט>>` | `Project.Number` | ✅ כן | מספר הפרויקט |
| `<<ישוב>>` | `Project.Place.Title` | ✅ כן | שם הישוב |
| `<<רשות מקומית>>` | `Project.Place.Title` | ✅ כן | זהה לישוב |
| `<<תאריך>>` | `Report.InspectionDate` | ✅ כן | תאריך הביקורת |
| `<<ממלא דוח>>` | `Report.InspectorName` | ✅ כן | שם הבודק |
| `<<כתובת מייל>>` | `Report.Inspector.Email` | ✅ כן | מייל הבודק |
| `<<מספר דוח>>` | `Report.ReportNumber` | ✅ כן | מספר סידורי |
| `<<Today>>` | `Report.InspectionDate` | ✅ כן | תגית אנגלית — תאריך |
| `<<User>>` | `Report.InspectorName` | ✅ כן | תגית אנגלית — שם בודק |
| `<<Email>>` | `Report.Inspector.Email` | ✅ כן | תגית אנגלית — מייל |
| `<<כתובת>>` | ידני | ❌ לא | כתובת האתר — מילוי ידני |
| `<<יזם התכנית>>` | ידני | ❌ לא | מילוי ידני |
| `<<מתכנן התכנית>>` | ידני | ❌ לא | מילוי ידני |
| `<<מספר מגרש>>` | ידני | ❌ לא | מילוי ידני |
| `<<תאריך קבלת התוכנית>>` | ידני | ❌ לא | מילוי ידני |
| `<<מספר תכנית>>` | ידני | ❌ לא | מילוי ידני |
| `<<גוש (חלקה)>>` | ידני | ❌ לא | מילוי ידני |
| `<<סוג נספח התנועה>>` | ידני | ❌ לא | מילוי ידני |

> **הערה:** שדות אוטומטיים מציגים כפתור "אוטומטי/ידני".  
> לחיצה על "ידני" מאפשרת לדרוס את הערך האוטומטי בטקסט חופשי.

## 3. תגיות סעיפים ממוספרים (Section Tags)

כל סעיף ביקורת מזוהה על ידי **קוד מספרי** בפורמט `X.Y` (למשל `1.1`, `2.4`, `3.12`).

### 3.1 תגית הגדרה (Status Tag)

```
<<X.Y כותרת פרק [תוכן הסעיף]>>
```

**חלקים:**
- `X.Y` — קוד הסעיף (מספר פרק.מספר סעיף)
- `כותרת פרק` — שם הפרק (חייב להיות זהה לכל הסעיפים באותו פרק)
- `[תוכן הסעיף]` — שם הסעיף בתוך סוגריים מרובעים

**דוגמה:**
```
<<1.1 כללי [תרשים סביבה, חץ צפון, גבול תוכנית לאישור]>>
<<1.2 כללי [קנ"מ ומידות]>>
<<2.1 חנייה [מספר חניות תקני]>>
```

> בייצוא — תא זה יוחלף בסטטוס מצטבר: **מקובל** / **הערה** / **הערה חוזרת** / **לא רלוונטי**

### 3.2 תגית קלט הערות (Note Input Tag)

```
<<X.Y $>>
```

סימן ה-`$` מציין את התא שבו יוזרקו הערות הבודק.  
תומך גם בסדר הפוך (RTL): `<<$ X.Y>>`

**דוגמה:**
```
<<1.1 $>>
<<$ 2.4>>
```

### 3.3 כלל הצמדים (Pairing Rule)

**כל סעיף חייב להכיל בדיוק שתי תגיות:**

| תגית | תפקיד |
|-------|--------|
| `<<X.Y כותרת [תוכן]>>` | הגדרה + סטטוס |
| `<<X.Y $>>` | קלט הערות |

אם חסרה אחת מהן — המערכת תציג שגיאת תיקוף.

## 5. כללי תיקוף (Validation Rules)

המערכת מפעילה **בודק תקינות** לפני כל סנכרון או ייצוא:

### כלל 1: עקביות כותרת פרק (`CHAPTER_TITLE_MISMATCH`)
כל הסעיפים באותו פרק (למשל `1.1`, `1.2`, `1.3`) חייבים לשתף את אותה כותרת פרק.

❌ **שגוי:**
```
<<1.1 כללי [תרשים]>>
<<1.2 חנייה [מידות]>>     ← "חנייה" ≠ "כללי"
```

✅ **תקין:**
```
<<1.1 כללי [תרשים]>>
<<1.2 כללי [מידות]>>
```

### כלל 2: תג הגדרה יחיד (`DUPLICATE_DEFINITION`)
לכל קוד סעיף מותר **תג הגדרה אחד בלבד** (עם סוגריים מרובעים).

❌ **שגוי:**
```
<<1.1 כללי [תרשים]>>
<<1.1 כללי [חץ צפון]>>   ← כפילות!
```

### כלל 3: חובת צמד (`MISSING_NOTE_INPUT` / `MISSING_HEADER`)
כל סעיף חייב לכלול **גם תג הגדרה וגם תג קלט `$`.**

❌ **שגוי — חסר קלט:**
```
<<1.1 כללי [תרשים]>>
(ללא <<1.1 $>>)
```

❌ **שגוי — חסר הגדרה:**
```
<<1.1 $>>
(ללא <<1.1 כללי [תרשים]>>)
```

### כלל 4: מגבלת כפילויות (`EXCESS_DUPLICATE`)
כל קוד סעיף יכול להופיע **מקסימום 2 פעמים** (הגדרה + קלט).

❌ **שגוי:**
```
<<1.1 כללי [תרשים]>>
<<1.1 $>>
<<1.1 נוסף>>              ← הופעה שלישית!
```

### כלל 5: סעיף אב חסר (`ORPHAN_SECTION`) — חדש
סעיף `X.Y.Z` (תת-סעיף) חייב שיהיה לו סעיף אב `X.Y`.

❌ **שגוי:**
```
<<1.1.2 כללי [פרט]>>     ← אין 1.1 בתבנית
```

### כלל 6: תגית ריקה (`EMPTY_TAG`) — חדש
תגית ללא תוכן היא שגיאה.

❌ **שגוי:**
```
<<  >>
<<>>
```

### כלל 7: עמודת תגובת המתכנן — חובה (`MISSING_PLANNER_RESPONSE_TAG` / `DUPLICATE_PLANNER_RESPONSE_TAG`)

התבנית **חייבת** לכלול את התגית הבאה **בדיוק פעם אחת**:

```
<<תגובת המתכנן>>
```

- התא שבו מופיעה התגית קובע את **העמודה הרשמית** שבה ייכתבו וייקראו תגובות / הערות המתכנן.
- בעת יצירת הדוח החדש המערכת מחליפה את התגית בכותרת רגילה: `תגובת המתכנן`.
- המערכת **כבר לא** מזהה את עמודת תגובות המתכנן לפי מיקום יחסי (שתי עמודות אחרי מספר הסעיף). הזיהוי נעשה אך ורק לפי התגית הזו.

**הודעות שגיאה אפשריות:**

❌ אם התגית חסרה:
```
לא נמצאה עמודת תגובת המתכנן בתבנית
```

❌ אם התגית מופיעה יותר מפעם אחת:
```
תגית עמודת תגובת המתכנן יכולה להופיע רק פעם אחת בתבנית
```

> **הערה:** אם בעת יצירת דוח חלק מהסעיפים שנמצאו בתבנית לא נכנסו לדוח, התהליך לא נעצר —
> מוצגת הודעה לא חוסמת ("הדוח נוצר, אבל לא כל הסעיפים מהתבנית נכנסו לדוח. נא לבדוק את הלוג.")
> ובלוג נרשמת אזהרה לכל סעיף חסר עם `Operation=ReportBuildValidation`.

## 6. דוגמאות: תקין ✅ מול שגוי ❌

### דוגמה א': סעיף תקין

✅ **תקין:**
```
תא A5:  <<1.1 כללי [תרשים סביבה, חץ צפון]>>
תא B5:  <<1.1 $>>
```
→ המערכת תזהה סעיף 1.1, תציג סטטוס בתא A5 והערות בתא B5.

### דוגמה ב': כפילות הגדרה

❌ **שגוי:**
```
תא A5:  <<1.1 כללי [תרשים סביבה]>>
תא A8:  <<1.1 כללי [חץ צפון]>>
תא B5:  <<1.1 $>>
```
→ שגיאה: `"מזהה '1.1' מכיל 2 תגי הגדרה — מותר אחד בלבד."`

### דוגמה ג': שדה כללי

✅ **תקין:**
```
תא C2:  <<שם פרויקט>>
תא C3:  <<מספר פרויקט>>
תא C4:  <<Today>>
```
→ יוחלפו אוטומטית בנתוני הפרויקט.

### דוגמה ד': כותרות פרק לא עקביות

❌ **שגוי:**
```
<<1.1 תנועה [שילוט]>>
<<1.2 כללי [מידות]>>     ← כותרת "כללי" ≠ "תנועה"
```
→ שגיאה: `"תגים בפרק 1 מכילים כותרות שונות: 'תנועה', 'כללי'."`

## 7. סטטוסים ואגרגציה

בעת ייצוא, המערכת מחשבת **סטטוס מצטבר** לכל סעיף מתוך כל ההערות שלו:

| סטטוס | תווית עברית | צבע רקע | עדיפות |
|--------|-------------|---------|--------|
| `Failed` | הערה | 🔴 אדום | 1 (חזק ביותר) |
| `RecurringFailed` | הערה חוזרת | 🔵 כחול | 2 |
| `Passed` | מקובל | 🟢 ירוק | 3 |
| `NotApplicable` | לא רלוונטי | ⚪ אפור | 4 (חלש ביותר) |

**כלל האגרגציה:** הסטטוס ה"חזק" ביותר מנצח.  
למשל: אם סעיף מכיל 3 הערות — 2 "מקובל" ו-1 "הערה" → הסטטוס המצטבר הוא **"הערה"** (אדום).

## 8. טיפים ושיטות עבודה מומלצות

1. **תמיד צרו צמד** — תג הגדרה `[...]` + תג קלט `$` לכל סעיף.
2. **שמרו על עקביות כותרות** — כל הסעיפים בפרק חייבים לשתף את אותה כותרת.
3. **השתמשו בשדות אוטומטיים** — חוסכים הקלדה ומונעים טעויות.
4. **בדקו לפני יצירת דוח** — המערכת מפעילה בודק תקינות אוטומטי.
5. **רעננו אחרי שינויים בתבנית** — שינוי בגוגל שיטס דורש רענון בממשק.
