# 📋 Migration Roadmap — Historical Data Import & Task Generation

## Overview

This document defines the **Migration Roadmap** and **Database Schema** for importing
historical inspection reports from the master Google Sheets index
("גליון דוחות בדיקת תנועה") into the SQL inspection system, and auto-generating
`ProjectAssignment` tasks based on each row's status.

> **⚠ CRITICAL**: The report sheets are **FINAL/filled exports**, NOT templates.
> There are **NO `<<...>>` tags** in these sheets — tags were replaced during export
> with actual values (status labels, note text) and background colors.
> Extraction uses a **two-phase approach**: scan the TEMPLATE for cell-position mapping,
> then read the FINAL report at those positions to get actual text + background color.

---

## 1. Data Source — Index Sheet Layout

| Column | Field            | Usage                                              |
|--------|------------------|----------------------------------------------------|
| A      | Project ID       | Numeric ID matching `Projects.Number` (float)      |
| B      | Project Name     | Display name — used only if project doesn't exist   |
| E      | Report Sheet URL | Link to the individual Google Sheets report         |
| F      | Status (Hebrew)  | e.g., "ממתין לתיקון", "אושר", "בבדיקה פנימית"     |
| K      | Inspector Email  | Matched to `Siusers.Email` for task assignment      |

### Special Cases
- **Project "9999"** → Unassigned projects. The service creates (or reuses) a
  temporary `Project` entity with `Number = 9999` and `Title = "לא משויך"`.
- **Missing email** → Task is created with `AssignedToId = null` (unassigned).
- **Blank Column E** → Row is skipped (no report link to follow).

## 2. Database Schema — New Entities

### 2.1 `MigrationRun` — Audit Trail

Tracks each execution of the migration process for idempotency and debugging.

```
Table: MigrationRuns
──────────────────────────────────────────────────────────
RunId              int           PK, Identity
StartedAt          datetime2     NOT NULL
CompletedAt        datetime2     NULL
Status             nvarchar(50)  "Running" / "Completed" / "Failed"
TotalRows          int           Total rows in index sheet
ProcessedRows      int           Rows successfully processed
SkippedRows        int           Rows skipped (blank URL, errors)
FailedRows         int           Rows that failed extraction
CreatedByUserId    int           FK → Siusers (who triggered it)
ErrorLog           nvarchar(MAX) NULL — aggregated error messages
```

### 2.2 `MigrationRowLog` — Per-Row Detail

One entry per index-sheet row per migration run. Enables re-running
only failed rows without re-processing successes.

```
Table: MigrationRowLogs
──────────────────────────────────────────────────────────
RowLogId           int           PK, Identity
RunId              int           FK → MigrationRuns
IndexRowNumber     int           1-based row in the index sheet
ProjectNumber      float?        Parsed from Column A
SpreadsheetId      nvarchar(500) Extracted from Column E URL
Status             nvarchar(50)  "Success" / "Skipped" / "Failed"
ReportId           int?          FK → InspectionReports (if created)
TaskId             int?          FK → ProjectAssignments (if created)
ErrorMessage       nvarchar(MAX) NULL
ProcessedAt        datetime2     NOT NULL
```

### 2.3 No New "InspectionTask" Entity

**Key design decision:** We reuse the existing `ProjectAssignment` entity
for inspection-related tasks. The `TaskType` lookup table will have a new
entry for "ביקורת תנועה" (Traffic Inspection) to distinguish migration-created
tasks from regular assignments.

### 2.4 New `TaskType` Seed Data

| Name              | SortOrder | Purpose                        |
|-------------------|-----------|--------------------------------|
| ביקורת תנועה      | 100       | Tasks generated by migration   |

### 2.5 New `ProjectAssignmentStatus` Seed Data (if not existing)

The migration maps Hebrew status strings to `ProjectAssignmentStatus`:

| Hebrew Status            | Maps To Status Name     | IsOpen | Priority |
|--------------------------|------------------------|--------|----------|
| ממתין לתיקון             | ממתין לתיקון            | true   | High     |
| בבדיקה פנימית            | בבדיקה                  | true   | Normal   |
| בבדיקה                   | בבדיקה                  | true   | Normal   |
| ממתין לבדיקה חוזרת       | ממתין לבדיקה חוזרת      | true   | High     |
| אושר                     | אושר                    | false  | —        |
| הושלם                    | הושלם                   | false  | —        |
| *(anything else)*        | חדש                     | true   | Normal   |

## 3. Migration Phases (Roadmap)

### Phase 1: Schema & Seed Data
1. Create `MigrationRun` model + EF configuration.
2. Create `MigrationRowLog` model + EF configuration.
3. Register both in `SiNetSQLDbContext`.
4. Seed the new `TaskType` entry ("ביקורת תנועה").
5. Generate EF migration (user runs `Add-Migration` command).

### Phase 2: Index Sheet Reader (`IndexSheetReader`)
A service class in `SiNetProjectManager.Services` that:
1. Reads the index sheet using Google Sheets API (`Values.Get`).
2. Parses each row into an `IndexSheetRow` DTO:
   ```
   IndexSheetRow
   ├── RowNumber        (int)
   ├── ProjectNumber    (float?)
   ├── ProjectName      (string?)
   ├── ReportSheetUrl   (string?)   — Column E
   ├── SpreadsheetId    (string?)   — extracted from URL
   ├── StatusText       (string?)   — Column F (Hebrew)
   ├── InspectorEmail   (string?)   — Column K
   ```
3. Filters out empty/header rows.
4. Returns `IReadOnlyList<IndexSheetRow>`.

### Phase 3: Report Content Extractor (`ReportContentExtractor`) ✅ PoC IMPLEMENTED
A service class in `SiNetProjectManager.Services.Migration` — **already built as PoC**.

**Two-phase extraction strategy** (reports are FINAL, no tags):
1. **Template scan**: Reads the TEMPLATE spreadsheet with `ScanAllTemplateTags()`
   to discover cell-to-section mapping (section code → row/col for status + note cells).
2. **Report read**: Reads the FINAL report with `includeGridData=true` (gets values + formatting).
3. **Positional matching**: For each template-mapped position, walks forward through
   the final report accounting for row shifts from multi-note insertions.
4. **Status detection**: Background color classification (±0.08 tolerance):
   - `{R:0.85, G:0.95, B:0.85}` → Light green → `Passed`
   - `{R:0.95, G:0.85, B:0.85}` → Light red → `Failed`
   - `{R:1.00, G:0.93, B:0.80}` → Light orange → `RecurringFailed`
   - `{R:0.93, G:0.93, B:0.93}` → Light gray → `NotApplicable`
5. **Fallback**: Text-based inference ("מקובל"→Passed, "הערה"→Failed, etc.)
6. **Multi-note handling**: Detects inserted rows below note cells and concatenates.
7. Returns a `ReportExtractionResult`:
   ```
   ReportExtractionResult
   ├── Sections              List<ExtractedSectionData>
   │   ├── SectionCode       (string, e.g., "1.1")
   │   ├── ChapterTitle      (string)
   │   ├── SectionTitle      (string)
   │   ├── StatusText        (Hebrew label from cell)
   │   ├── StatusKey          (string — "Passed"/"Failed"/...)
   │   ├── StatusColorHex    (hex color of status cell)
   │   ├── NoteText           (string)
   │   ├── NoteSubIndex      (string, e.g., "1.1.1")
   │   ├── ReportRow          (actual row in final report)
   │   └── DetectionMethod   ("direct-offset" / "color-scan" / "text-only")
   ├── GeneralFields         Dictionary<string, string>
   └── Warnings              List<string>
   ```

**Test window**: `MigrationPocWindow` — accessible via מנהלה → 🔬 בדיקת חילוץ דוח.
Paste a template ID and a final report ID/URL, click Extract, see results in DataGrid + JSON.

### Phase 4: Data Import Service (`MigrationImportService`)
A service class in `SiNetSQL.Services` that:
1. Receives a `ReportExtractionResult` + project/user context.
2. **Project resolution:**
   - Lookup `Project` by `Number` (from Column A).
   - If not found and Number == 9999 → create/reuse "לא משויך" project.
   - If not found and Number != 9999 → create project with `Title` from Column B.
3. **Series resolution:**
   - Find or create `InspectionSeries` for the project using the template spreadsheet ID.
4. **Chapter/Section sync:**
   - For each unique chapter number in extracted sections, find-or-create `Chapter` + `ChapterName`.
   - For each section, find-or-create `Section` + `SectionName`.
5. **Report creation:**
   - Create `InspectionReport` with `ReportNumber = 1` (first import), `InspectionDate = DateTime.Now`.
   - Link to project, series, inspector (resolved by email).
6. **Note creation:**
   - For each `ExtractedSection`, create `InspectionNote` linked to the report + section.
   - Set `NoteStatus` (legacy) and `NoteStatusId` (lookup).
7. All operations wrapped in a single `SaveChangesAsync()` per report.

### Phase 5: Task Generator (`MigrationTaskGenerator`)
A service class in `SiNetSQL.Services` that:
1. Receives the `IndexSheetRow` + the created `InspectionReport`.
2. Checks Column F status — if NOT "אושר" or "הושלם":
   - Creates a `ProjectAssignment` with:
     - `ProjectId` = resolved project ID
     - `Title` = $"ביקורת תנועה — {projectName}"
     - `TaskTypeId` = "ביקורת תנועה" TaskType ID
     - `StatusId` = mapped from Hebrew status (see table in §2.5)
     - `Priority` = derived ("High" for "ממתין לתיקון"/"ממתין לבדיקה חוזרת", "Normal" otherwise)
     - `AssignedToId` = resolved from `Siusers.Email` (Column K)
     - `Body` = $"נוצר אוטומטית ממיגרציה — גליון: {spreadsheetId}"
     - `Created` = `DateTime.UtcNow`
3. Returns the `ProjectAssignment.Id` for logging.

### Phase 6: Orchestrator (`MigrationOrchestrator`)
The top-level service that ties everything together:
1. Creates a `MigrationRun` record.
2. Calls `IndexSheetReader` to get all rows.
3. Processes rows in **batches of 10** with a **2-second delay** between batches
   (Google API rate limiting: 60 requests/min/user).
4. For each row:
   a. Log `MigrationRowLog` with status "Processing".
   b. Call `ReportContentExtractor` → extract content.
   c. Call `MigrationImportService` → create report + notes.
   d. Call `MigrationTaskGenerator` → create task (if needed).
   e. Update `MigrationRowLog` with result.
5. Updates `MigrationRun` with final counts.
6. Supports `CancellationToken` for graceful cancellation.
7. Supports **resume** — skips rows that already have `Status = "Success"` in a previous run.

## 4. API Rate Limiting Strategy

```
┌──────────────────────────────────────────────────────────────┐
│ Google Sheets API Quota: 60 read requests/min/user           │
│                                                              │
│ Strategy:                                                    │
│   • Batch size: 10 rows per batch                            │
│   • Delay: 2000ms between batches                            │
│   • Per-row reads: 1 (Values.Get for entire sheet)           │
│   • Effective: ~30 sheets/minute (safely under quota)        │
│   • Exponential backoff on 429 errors (2s → 4s → 8s → 16s)  │
│   • Max retries per row: 3                                   │
└──────────────────────────────────────────────────────────────┘
```

## 5. RTL / Mirror Text Handling

1. **All cell text** passes through `StripBidiMarks()` before regex matching.
2. `NoteInputTagRegex` already supports both `<<X.Y $>>` and `<<$ X.Y>>` orderings.
3. Extracted `NoteText` is stored as-is (preserving Hebrew) — only BiDi control
   characters are stripped.
4. Status detection uses case-insensitive, culture-invariant matching for English
   keys ("V", "X", "!") and `OrdinalIgnoreCase` for Hebrew labels.

---

## 6. Error Handling & Idempotency

- **Idempotent re-runs:** Each `MigrationRowLog` records the spreadsheet ID.
  On re-run, rows with `Status = "Success"` are skipped automatically.
- **Partial failure:** If a row fails (API error, parse error), it's logged as
  "Failed" and processing continues with the next row.
- **Duplicate detection:** Before creating an `InspectionReport`, the service
  checks if one already exists for the same `ProjectId + SeriesId + ReportNumber`.
  If found, the row is marked "Skipped (already exists)".
- **Transaction safety:** Each row is processed in its own DB transaction.
  A single-row failure cannot corrupt other rows.
